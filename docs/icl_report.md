# 基于上下文学习的 LLM 多智能体通信：Switch 任务实验汇报

## 1. 背景与目标

上一阶段用 LoRA + REINFORCE 微调 Qwen2.5-0.5B，训练 1001 轮后模型收敛到"永远开灯、永远不宣布"，测试奖励为 0。

根据导师意见：
- 这个任务的信息密度太低（一局只有一个 ±1 的团队奖励），不适合做权重微调；
- 改为从**上下文学习（ICL）**入手：不训练任何参数，用提示词和显式外部记忆（`protocol.md`、`memory.md`）搭建智能体之间的通信框架；
- **每个智能体使用独立的 LLM 实例**，避免共享 KV cache 带来意料之外的关联。

本阶段要回答三个问题：

| 实验 | 问题 |
|---|---|
| E1 给定协议 | LLM 能否仅靠上下文，执行一份人写的最优通信协议？ |
| E2 赛前商定 | LLM 能否自己设计出可用的协议？ |
| E3 复盘迭代 | LLM 能否通过赛后复盘逐轮改进协议？ |

---

## 2. 实验框架

### 2.1 与原任务保持一致的部分
- 3 个囚犯，6 天；每天随机一人进房间，看到前一天的灯，可以开灯、关灯或宣布"所有人都来过了"。
- **比赛中唯一的通信信道仍然是 1 bit 灯泡**，奖励和归一化指标与原论文相同。
- 两条参照线：
  - **0.65**：不通信也能拿到（只在第 6 天宣布）。我另外穷举验证过：只利用"第几天"和"是否第一次来"这两个信息，最好也只能达到 0.65。所以**超过 0.65 才说明用到了通信**。
  - **1.0**：最优协议（附录 A）。

### 2.2 上下文学习的设计
- **自然语言交流只发生在比赛外**：赛前开会商定协议、赛后复盘。比赛中只能靠灯泡。这对应经典囚徒谜题里"开局前可以开会"，也对应原论文的"集中学习、分散执行"。
- **比赛中每个智能体能看到的上下文**（由代码保证信息隔离，检查过 450 个决策，没有一处泄漏）：

| 部分 | 内容 |
|---|---|
| `protocol.md` | 所有人共享的协议：E1 由人给定，E2/E3 由智能体商定 |
| `memory.md` | 程序自动记录的自己的访问历史，加上智能体自己写的笔记 |
| 今天的观测 | 第几天、看到的灯、昨天是不是自己 |

- **商定协议的流程**：3 人轮流发言 2 轮 → 1 号整理成 `protocol.md` → 其他人审阅 → 有意见时 1 号修改一次。
- **复盘（E3）**：所有人看到本轮统计和失败对局的完整记录，总结经验写进 `lessons.md`，下一轮带着这些重新商定协议。

### 2.3 评价指标
除归一化奖励外，后来又加了几项能解释"为什么"的指标：
- **按规则统计的执行正确率**：把每个决策和最优协议的 4 条规则对比（附录 A 中的 R1–R4）；
- **宣布分析**：宣布时看到的灯、是第几天、是不是第一次来。正确的协议只在灯 ON 时宣布；
- **协议检查**：让模型把协议"编译"成一张决策表（29 种局面 → 动作），再穷举所有 729 种来访顺序，算出"所有人都完美执行时这份协议能得多少分"。这样可以把"协议设计得好不好"和"执行得好不好"分开。

## 3. 实验环境

| 项目 | 设置 |
|---|---|
| 模型 | Qwen2.5-3B-Instruct（0.5B 只用于跑通流程） |
| 硬件 | RTX 4080 Laptop（12 GB），Windows，transformers 进程内推理，bfloat16 |
| 解码 | 比赛中贪心（温度 0）；商定 / 复盘时温度 0.7 |
| 智能体实例 | 3 个智能体分别调用，各自的上下文和 KV cache 互不共享。**由于显存限制，3 个智能体共用同一份只读权重**，见第 6 节第 4 点 |

## 4. 实验结果

### 4.1 框架验证（不用模型）
用一个按最优协议作答的"规则智能体"替换 LLM，走完整流程（商定 → 比赛 → 复盘 → 协议检查 → 续跑）：
- 归一化奖励 **1.0**，协议检查 1.0，规则正确率 100%；
- 信息隔离、断点续跑都验证通过。

结论：环境、奖励、提示词里提供的信息和评价工具都是正确的。LLM 表现不好时，可以排除框架本身的问题。

### 4.2 第一轮：E1 / E2 / E3（自由推理，每轮 32 局）

| 实验 | 轮数 | 每轮归一化奖励 | 均值 |
|---|---|---|---|
| E1 给定协议 | 4 | 0, 0, 0, 0 | **0.00** |
| E2 赛前商定 | 4 | −0.04, −0.08, 0.04, −0.25 | −0.08 |
| E3 复盘迭代 | 10 | 0.13, −0.08, 0.29, 0.05, 0.00, 0.07, 0.08, 0.14, 0.04, −0.08 | 0.06 |

三个实验都远低于不通信的 0.65。

**E1：从不宣布**

| 规则 | 应该怎么做 | 次数 | 正确率 |
|---|---|---|---|
| R1 | 灯 ON 且第一次来 → 宣布 | 122 | **0.00** |
| R2 | 灯 ON → 保持 ON | 320 | 0.97 |
| R3 | 灯 OFF、不是第 1 天、昨天不是自己 → 开灯 | 125 | 0.46 |
| R4 | 其他情况 → OFF | 201 | 0.65（35% 误开灯） |

- 在 122 个应该宣布的局面里，模型的推理中一次都没出现过 "announce"。
- 30% 的输出先给答案、后补推理；34% 的笔记照抄了模板里的占位文字。

**E2：商定出的协议没有逻辑**

商定的协议没有写清楚什么时候宣布，用的是"之前每天都在房间里"这类几乎不可能成立的条件。第 2 天宣布了 8 次，全部输掉（第 2 天最多只有 2 人来过，不可能赢）。

**E3：分数偶尔上升，但不是通信带来的**
- 10 轮的协议都没有逻辑：宣布的条件是"灯的状态符合你的预测"，但"预测"从未定义。复盘后加的规则都是比赛中做不到的，比如"和其他囚犯协调"。
- 61 次宣布中，**49 次是在灯 OFF 时做出的**，而正确的协议只在灯 ON 时宣布。
- 赢的局靠的是"我是第一次来、日期又比较晚"。例如"第 3 天、第一次来"时宣布的胜率是 56%，而完全不看灯的理论胜率是 50%。
- 分数最高的一轮（0.29）里，16/21 次宣布发生在第 3 天。策略"第一次来且已到第 3 天就宣布"的理论分数是 **0.28**，两者几乎一样。
- 噪声：策略固定不变时，每轮 32 局的奖励标准差约 **0.2**。E3 的 10 轮波动都在噪声范围内，看不出跨轮次的学习。
- 后几轮因为复盘中"防止过早宣布"这类经验，变得不敢宣布：输的次数变成 0，赢的次数也一起减少。这和 RL 实验里的现象类似。

### 4.3 第二轮：改进提示词后的 E1（每轮 64 局）
针对第一轮的问题，提示词做了三处改动：
1. 把"是否第一次来、昨天在不在"等事实逐条写明；
2. 回复格式固定为 `FACTS → RULE（引用规则）→ CHECK → JSON`；
3. 预填回复开头，保证先推理后作答。

**结果**：4 轮奖励为 −1.33、−1.45、−1.33、−1.36。**每局都在第 1 天宣布，全部输掉。**

- 典型输出：FACTS 写对了（灯 OFF、第一次来），RULE 却引用了规则 1（灯 ON 且第一次来 → 宣布）。
- 协议检查编译出的决策表只有 38/87 和最优协议一致，规律是**"只要第一次来就宣布，不看灯"**。

### 4.4 第三轮：只做协议编译，对比三种回复格式
完整对局成本高，之后改用"协议编译"做快速对比：每种格式 29 个局面，GPU 上 1–2 分钟。

| 格式 | 和最优协议一致 | 完美执行分数 | 模型实际怎么做 |
|---|---|---|---|
| A. FACTS → RULE → CHECK（第二轮的格式） | 14/29（两次运行结果相同） | −1.35 | 会推理，但只核对了条件的一半：第一次来就宣布 |
| B. 逐条写条件 yes/no（第一版模板） | 20/29 | 0.00 | **没有推理**：22/29 条输出原样照抄了模板里的 "yes/no"，一个 yes/no 都没填，然后凭直觉给出动作，从不宣布 |
| C. 逐条写条件 yes/no（修正模板 + 加示例） | 10/29 | −1.35 | 真的填写了 yes/no，但规则 1 下写的是规则 3 的条件（29/29），而且 51 行判断中有 34 行和自己写的 yes/no 矛盾 |

格式 C 的一条典型输出（第 3 天、灯 OFF、昨天自己在房间，应该关灯）：
```
Rule 1: it is not day 1 = yes; you were the prisoner in the room yesterday = yes -> does not apply
...
DECISION: Rule 1 -> ANNOUNCE
```
规则 1 下写的是别的规则的条件；两个条件都是 yes 却判"不适用"；最后又说规则 1 适用，选择了宣布。

## 5. 分析与结论

1. **框架本身是正确的**：规则智能体得到 1.0，信息隔离和评价工具都经过验证。
2. **Qwen2.5-3B 无法仅靠上下文执行一份 4 条规则的自然语言协议**。三种提示格式各自失败，只是失败的位置不同：

| 格式 | 失败方式 |
|---|---|
| 自由推理 | 从不宣布 |
| 引用规则 | 只看一半条件，第一次来就宣布 |
| 逐条核对 | 条件张冠李戴，判断前后矛盾 |

3. **共同原因是"按字面匹配"**：模型会套用和事实描述字面最相近的那条规则（或那段条件），而不是真正判断"条件 A 且条件 B"。比如规则 3 的措辞和事实描述几乎一字不差，模型就把它的条件写到了规则 1 下面。提示格式只改变了哪一段更显眼，所以行为会在"从不宣布"和"总是宣布"之间翻转。
4. **执行能力不够时，E2/E3 的结论没有意义**：
   - 3B 连正确的协议都执行不了，所以它在 E2/E3 里商定出没有逻辑的协议也不意外；
   - E3 的分数上升来自"不需要通信的经验做法"加上采样噪声，不能说明学会了通信；
   - 协议检查也是用同一个模型编译协议，最优协议都被判成 −1.35，所以检查结果在 3B 上同样不可靠。
5. **方法上的收获**：
   - 只看奖励会产生误导。按规则统计正确率、分析宣布时看到的灯，才能分辨"是否真的用到了通信"；
   - 每轮 32 局时噪声标准差约 0.2，需要更大的批量（之后改为 64–128 局）和多次重复；
   - 协议编译只需要 29 次生成，可以在跑完整对局前快速筛选提示词和模型。

---

## 6. 存在的问题

1. **模型能力是当前的瓶颈**，目前只测试了 3B。
2. **E2/E3 只跑了一次，而且是在执行能力不足的前提下**，还不能用来回答"LLM 能否设计 / 改进协议"。
3. **协议检查依赖模型自己来理解协议**，模型能力不够时检查结果也不可信。另外，检查时会把结果反馈给智能体用于修改协议，这相当于给了智能体一个"推演协议的工具"，需要单独用"只记录、不反馈"的模式做对照。
4. **独立实例的实现**：本机单卡 12 GB 放不下 3 份 3B 权重，所以 3 个智能体共用一份只读权重。每次调用都新建 KV cache，不同智能体的请求不放进同一个 batch，相互之间不共享任何状态。如果需要严格的进程级隔离，可以在服务器上为每个智能体单独启动一个 vLLM 服务，框架已经支持。

---

## 7. 下一步计划

1. **换更强的模型，先过 E1 这一关**：
   - 首选 **Qwen3-4B（带思考模式，单卡可运行）**，用协议编译快速对比；
   - 备选 Qwen2.5-7B 的 4-bit 量化版。
   - 标准：编译一致数接近 29/29，并且灯 ON 且第一次来时会宣布，才进入完整的 E1。
2. **E1 通过后，再跑 E2 / E3**：
   - 每轮 128 局，多个随机种子；
   - 协议检查分"只记录"和"不合格就打回修改"两组做对照。
3. **通信消融（核心研究问题）**：灯泡不可见 vs 可见；干预测试（只改变 prompt 里的灯泡状态，看决策是否随之改变），检验模型是否真的在"听"信号。

**需要导师确认的问题**：
- 换用 Qwen3-4B 等更大或带推理能力的模型，是否符合"轻量开源模型"的研究设定？
- 如果更大的模型仍然不行，能否把协议写成结构化形式（每条规则明确列出条件和动作），降低对自然语言理解的要求？
- 协议检查的结果反馈给智能体修改协议，这种做法是否可以接受？还是只作为评价工具使用？

## 附录 A：最优协议（3 人，E1 使用）

灯 ON 表示"至少已有 2 个不同的人来过"。进门时按顺序使用第一条符合的规则：

1. 灯 ON，且这是我第一次来 → **宣布**（R1）
2. 灯 ON → 保持 ON（R2）
3. 不是第 1 天，并且昨天在房间的不是我 → 开灯（R3）
4. 其他情况 → 关灯（R4）

这个协议从不宣布错误，而且只要所有人都来过就一定有人宣布，所以归一化奖励为 1.0。
